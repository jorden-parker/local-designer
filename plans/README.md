## Direction findings not planned (available on request)

- **DIR-03 Import an existing project's tokens.** The handoff
  (`src/lib/handoff/handoff.ts:10-11`) tells the implementer to map tokens onto
  "this project's own design system", but a design can only start from a brief
  (`POST /api/designs`, `createDesign(directory, brief)`). Tokens are already
  zod-validated (`src/lib/design/tokens.ts`), so accepting an optional
  `tokens.json` on create and seeding system v1 from it is one route change plus
  a form disclosure. Effort M. Not planned because its value depends on whether
  designs are usually for existing products; components import is harder and
  should stay out of a first slice.
- **DIR-06 Design housekeeping.** No rename, delete or duplicate for designs or
  pages (`src/app/api/designs/**` has no DELETE; the title is only ever
  `titleFrom(brief)`), and the gallery thumbnail is a placeholder dot grid
  (`src/components/gallery/design-list.tsx:24`). Effort S-M. "Archive" fits the
  never-lose-history promise better than delete. Not planned because the value
  is modest for a single local user.

## Findings considered and rejected

- **Server-side render check during review** (run model code with
  `react-dom/server` inside `check` so runtime errors reach the repair turn):
  crosses the stated trust boundary (generated code runs only in the
  opaque-origin iframe). Plan 004 takes the client-side route instead.
- **Direct manipulation (drag, resize, inline text editing)**: the product's
  premise is that a model makes the change from a request scoped to an element;
  direct editing would need a second code-mutation path and is at odds with the
  3B-model constraint.
- **Multi-element selection**: the element prompt and `replaceElement` are
  single-root by design; a 3B model handling several disjoint replacements in
  one reply is unlikely to be reliable.
- **Real images / icon packs in wireframes**: image placeholders are a rule in
  `TOKEN_RULES` on purpose; wireframes settle layout, not assets.
